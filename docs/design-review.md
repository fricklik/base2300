# 独立公開の設計レビュー

## 結論

Base2300 は、**元データを完全に復元できる範囲で Unicode コードポイント数を減らす実験**として公開する。
UTF-8 の容量削減、暗号化、LLM トークン削減を保証するものではない。
CRC32 付き v1 を基本 API、CRC なし・予測圧縮・ネイティブ圧縮を実験 API として分け、
元プロジェクト専用の LLM サービスを依存関係から外す方針を採用した。

以下の判断は実装の読み取りとローカルの検証によるもの。
外部モデルによるレビュー回答は 2 回目の実施で取得した（フォールバックモデル。次節）。

## 実コードで確認した判断

| 判断 | 根拠 | 確信度 |
| --- | --- | --- |
| 文字数とバイト数を別々に公表する | 固定文字表は ASCII 64 字、UTF-8 3 バイトの文字 2,235 字、4 バイトの文字 1 字。フレームは 244 bit を 22 コードポイントへ変換する | 高 |
| JavaScript の `.length` を文字数と同一視しない | `𠮟`（U+20B9F）は 1 コードポイント、UTF-16 では 2 単位。文字表の残りは BMP 内 | 高 |
| 文字表・方式番号は固定する | 数値の桁値と minimal のヘッダは文字表の位置に直接依存する。変更すると保存済みの文字列の意味が変わる | 高 |
| LLM 番号を再利用しない | 既存の `き` と minimal mode index `7` は外部復号プロファイルを必要とする LLM 方式に割当済み | 高 |
| minimal は明示的な選択にする | `expandMinimalBase2300Frame` は CRC の場所にゼロを補い、呼び出し側は実 CRC の照合を省く。構造検証に通る誤記があり得る | 高 |
| CRC32 は認証として扱わない | CRC は復元した元バイト列に対する非秘密の決定的な計算。文字列を変更する側も計算し直せる | 高 |
| ヘッダの認識と形式の検証を分ける | `isBase2300` / `isMinimalBase2300` は先頭文字の判別のみ。残りの文字列の構造や内容は復号処理で検査する | 高 |
| 4 MiB の制限を CPU・メモリ全体の制限と呼ばない | フレーム・復元結果には上限があるが、候補ごとの中間配列、BigInt、予測復号後の再圧縮を実行する | 高 |
| ネイティブ候補は実行環境に依存する | `CompressionStream` / `DecompressionStream` の対応を実行時に調べる。送信側の利用可否だけでは受信側の復号可否を保証しない | 高 |

数値的な目安として、ヘッダを無視したバイナリ格納は元の 1 バイトにつき `8 × 22 / 244 ≈ 0.7213`
コードポイントを使う。桁が一様に分布すると仮定した UTF-8 の目安は約 `2.1241` バイト。
これは文字表から求めた近似であり、実際のブロックの桁分布は一様とは限らない。
本プロジェクトの性能結果は実測データを参照する。

### Unicode の確認

抽出後の文字表を Python で読み取り、2,300 字がすべて異なること、
非 BMP 文字が `𠮟` だけであること、minimal の既存ヘッダ 1,960 種が BMP に収まることを確認した。
NFC / NFKC はこの文字表を変えず、NFD / NFKD は `ゔ` と `ヴ` を分解する。
文字表の現在の不変性は、転送経路による異体字置換、大文字小文字の変換、折り返し挿入、
欠落、正規化一般への耐性を意味しない。

### 構造検証の確認

既存実装には、文字表外の文字、余計な先頭ゼロ、不正なブロック長、未割当の文字符号、
不要な Unicode エスケープ、非 scalar 値、復元量の超過を拒否する処理がある。
予測圧縮は元サイズを制限し、復号結果の再圧縮で非正規な終端や末尾データを検査する。
ネイティブ DEFLATE / Brotli は末尾を 1 バイト削ったストリームが復元できないことも検査する。
これらはコードで確認した性質であり、独立したセキュリティ監査や、未知の欠陥が存在しない保証ではない。

レビューでは、元のコードが DEFLATE のみにこの検査を適用しており、Node.js `v22.21.1` の
Brotli 実装では余計な末尾データを受理することを発見した。抽出版では Brotli にも検査を適用した。
修正後、両形式の空・テキスト・全 256 バイト値の正常データを復元でき、
各データに 4 種類の末尾を加えた合計 24 件を拒否することを別の実行で確認した。
正しい符号の生成と復元を変えず、不正な末尾を持つ入力の受理を厳しくする修正である。

### 切り出し前後の互換性

Node.js `v22.21.1` 上で、元プロジェクトの実装と抽出後のソースをそれぞれメモリ内で bundle し、
19 種類の固定入力を比較した。元 UI の LLM 依存は呼び出すと例外を投げる stub に置き換え、
LLM とネットワークは使用していない。

- CRC32 付き基本 API: 19 件。
- 実験 API の `full` / `fast`: 合計 38 件。
- ネイティブ圧縮候補を加えた API: 19 件。

すべてのケースで出力文字列、選択方式、候補ごとの文字数とステータスが一致し、
それぞれの出力を相手側で復号して全バイトの一致を確認した。
空、ゼロ、全 256 バイト値、不正 UTF-8、ASCII、日本語、英語、反復、BOM、結合文字、絵文字、
補助漢字、30 / 31 / 60 / 61 / 62 / 122 / 1,024 / 4,096 / 16,385 バイトの固定シード乱数を含む。
この入力群では minimal、短文日本語、予測 order 0 / 1 / 3、DEFLATE、Brotli が選ばれた。
経過時間は互換性の比較から除外した。

これは抽出による挙動差を探す比較であり、共通の元実装にある欠陥を発見する独立形式実装ではない。

## 公開と今後の研究

公開時には基本 API と実験 API の区別、ライセンスと文字表の出典、固定テストベクトル、
再現可能な測定スクリプト、制限と破損検出の説明を同梱する。
比較では元データ、Base64、同じ圧縮バイト列を用いた Base64 / Base2300、
CRC の有無を分け、ヘッダを含む全出力を計測する。

現時点で妥当な候補用途は、Unicode を変更せず扱える独自アプリの文字数制限欄、
実験用の設定共有文字列、文字集合と符号化効率の教材。
実サービスの採用例として実証したわけではない。
可読性、手入力、音読、OCR、URL、モデルへの意味理解用入力、バイト容量節約を重視する用途への適性は低い。

今後は未見の多言語コーパス、実際の転送経路、同じ破損検出条件での比較、
受信側能力の宣言、長期的な形式仕様と相互運用を調べる。
外部モデル相談の再実施も未完了の確認事項として残す。
